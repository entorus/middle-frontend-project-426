# Интернет-магазин комплектующих для ПК

[![hexlet-check](https://github.com/entorus/middle-frontend-project-426/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/entorus/middle-frontend-project-426/actions)

Разработайте интернет-магазин комплектующих для ПК целиком на TypeScript.
Фронтенд пишете на любом TS-фреймворке (React, Vue, Svelte, Angular, Solid и др.).
Готового API здесь нет, поэтому сервер под свой интерфейс вы поднимаете сами,
а фреймворк для него и работу с базой выбираете на свой вкус. Спроектируйте API
через TypeSpec → OpenAPI, реализуйте регистрацию и авторизацию, главную
с промо-блоками, каталог с фильтрами и пагинацией, корзину, оформление заказа
и личный кабинет с историей заказов. Приложение деплоится в прод с третьего шага
и развивается под собственными браузерными тестами.

Учебный проект Хекслета: https://ru.hexlet.io/programs/middle-frontend
Как это должно работать: https://files.hexlet.app/a/qf7bsq
Развёрнутое приложение: [PS Parts](https://middle-frontend-project-426-mynk.onrender.com/).

Откройте [локальное приложение](http://localhost:3000/catalog).

и 60 демонстрационных товаров, не удаляя данные и не создавая дубликаты.

```bash

npm ci
npm run test:smoke
docker compose exec -T app node dist/db/prepare.js
npm run test:smoke
docker compose down
```


Проверка компиляции обоих приложений: `npm run build` после установки зависимостей API и фронтенда.

## Карточка товара и корзина

На `/products/:id` показаны название, описание, изображение или заглушка, цена и наличие.
Кнопка добавления недоступна для отсутствующих товаров; перед добавлением наличие проверяется
ещё раз через существующий `GET /api/products/:id`. Контракт API и база на этом шаге не меняются.

Корзина доступна на `/cart`, ссылка `nav-cart` в шапке показывает суммарное количество.
В `localStorage` под ключом `psparts-cart` хранится только массив `[{ id, quantity }]`.
Названия, цены и изображения туда не записываются. Повторное добавление увеличивает количество
в существующей позиции. Количество — целое число от 1 до 999; удаление выполняется отдельной кнопкой.
При некорректном сохранённом JSON корзина восстанавливается пустой, некорректные позиции отбрасываются.
Если браузер запрещает запись, пользователь видит предупреждение о невозможности сохранения.

При каждом открытии корзины, возврате фокуса окна или ручном обновлении данные позиций
загружаются из каталога с `cache: no-store`. Итог вычисляется в копейках и отображается
в целых рублях. Удалённые, недоступные и непроверенные позиции выделены, не включаются в итог
и блокируют оформление до удаления или успешного обновления. Пустая корзина также блокирует переход.
Корзина не зависит от входа и выхода; серверной сущности корзины и синхронизации вкладок нет.

`/checkout` доступен только после входа. С пустой корзиной авторизованный пользователь
возвращается на `/cart`, гость — на форму входа с возвратом к оформлению.

## Оформление и история заказов

Форма `/checkout` запрашивает способ получения (`delivery` или `pickup`), имя и телефон.
Для доставки обязателен адрес одной строкой; для самовывоза поле адреса отсутствует.
Город и email не запрашиваются. Отдельной оплаты нет: созданный заказ имеет статус `paid` («Оплачен»).

Контракт в `main.tsp` описывает `POST /api/orders`, `GET /api/orders`, `GET /api/orders/{id}`.
Все операции требуют серверную сессию; список и отдельный заказ доступны только владельцу.
Неизвестный и чужой заказ одинаково возвращают 404. CSRF-проверка используется и при оформлении.

Тело запроса: `{ items: [{ id, quantity }], receiving: { method, name, phone, address? } }`.
Схема отклоняет лишние поля, включая цены, итог и чужой user_id. Пустой состав, неверное количество
и некорректные данные получения также отклоняются. Лимиты: 100 позиций, 1–999 единиц в позиции;
дублирующиеся идентификаторы не допускаются.

В транзакции PostgreSQL сервер находит все товары, проверяет наличие, вычисляет итог и сохраняет
заказ с позициями. Блокировка FOR SHARE удерживает выбранные товары от изменения до сохранения снимка.
Если есть проблемы, ответ 409 содержит ApiError и `products: [{ id, reason }]`, где reason —
`not_found` или `unavailable`. Заказ целиком откатывается, корзина остаётся у пользователя.

Миграция `006_create_orders` добавляет `orders` и `order_items`. В позиции сохранены название,
цена в копейках, количество и исторический ID товара без внешнего ключа на каталог: переименование,
изменение цены и удаление товара не меняют историю. Общий Money допускает безопасные целые числа
JavaScript; суммы заказов в БД — bigint, вычисления выполняются без дробных рублей.

После успешного ответа корзина очищается и открывается `/orders/:id/success`, где состав и итог
загружаются с сервера и переживают перезагрузку. Кабинет `/account` показывает собственные заказы
с датой, статусом, снимками позиций и итогом прямо в списке. При потере ответа оформления
проверьте историю перед повторной отправкой: API не выполняет автоматическую дедупликацию повторов.

Тесты PostgreSQL проверяют подмену полей, атомарность, снимок после удаления товара и изоляцию
пользователей с откатом тестовых изменений. Playwright проверяет форму, доставку/самовывоз,
ошибки, успех, очистку корзины и кабинет. Они включены в существующий CI.

Playwright проверяет карточку, добавление, количество и сумму, удаление, сохранение после
перезагрузки, актуальность цены, изменившееся наличие, исчезнувший товар и повреждённое хранилище.

## Главная и промо-блоки

На `/` — описание магазина, переход в каталог и подборка товаров из базы.
`GET /api/promotions` возвращает список `{ id, title, text, product }`: товар вложен
целиком, дополнительных запросов за каждой карточкой нет. Клик открывает `/products/:id`,
ту же страницу, что и ссылка из каталога. Ссылка `nav-catalog` остаётся в общей шапке.
При пустом списке показывается спокойное пустое состояние; при ошибке — кнопка повтора.

Миграция `005_create_promotions` создаёт таблицу `promotions` с внешним ключом на товар
и уникальным `product_id`: один товар не может рекламироваться дважды. Порядок определяется
полями `position`, затем `id`. API исключает недоступные товары на каждом запросе.
Сид `004_promotions` добавляет два блока на доступные CPU-001 и GPU-001, не перезаписывает
отредактированные тексты и не меняет наличие товаров. Для изменения рекламы обновите
`title`, `text` или `position` в БД — пересборка фронтенда не нужна.

Playwright проверяет загрузку главной, переходы, пустую подборку и повтор после ошибки.
Интеграционный тест проверяет ограничения и поведение с настоящей PostgreSQL; все его
изменения откатываются транзакцией. Запускать только с локальной тестовой БД:

```bash
TEST_DATABASE_URL=postgresql://psparts:local_password@127.0.0.1:55432/psparts npm run test:db
```

Перед тестом запустите Compose, чтобы применились миграции и сид. В CI этот тест также
запускается после готовности контейнеров (там PostgreSQL доступен на порту 5432).

## Каталог

Каталог доступен на `/catalog`; `/` — отдельная главная страница. Фильтры слева,
на узких экранах — над списком. Карточки содержат ссылку на `/products/:id`, краткое описание,
изображение или заглушку, цену в целых рублях и наличие. Недоступные товары остаются в выдаче.

`GET /api/products` фильтрует и разбивает данные на страницы в PostgreSQL. Ответ:
`{ items, total, page, pageSize, totalPages }`. Все параметры описаны в `main.tsp`:

- `category` — slug категории;
- `priceMin`, `priceMax` — целые рубли, границы включительно;
- `available=true` — только в наличии;
- `search` — часть названия без учёта регистра, символы `%` и `_` не являются масками;
- `page` — от 1, `pageSize` — от 1 до 48, по умолчанию 12.

Например: `/catalog?category=memory&priceMax=5000&available=true`.
Фильтры комбинируются и сохраняются в URL вместе со страницей. Смена фильтра сбрасывает
страницу на первую; перезагрузка, переходы назад/вперёд и передача ссылки сохраняют выдачу.
Поиск откладывается на 350 мс; устаревшие fetch-запросы отменяются через AbortController.
Значения контролов обновляются сразу. Ошибки загрузки можно повторить, пустая выдача показана явно.

Миграция `004_product_details` добавляет изображение и наличие. Сид `003_catalog` расширяет
исходные шесть товаров до 60: процессоры, видеокарты и память. Есть отсутствующие изображения,
недоступные позиции и разные цены; повторный сид не создаёт дубликаты. Новые товары и категории
добавляются по уникальным SKU и slug без перезаписи существующих данных.

`npm run test:e2e -- --workers=2` проверяет каталог вместе с авторизацией: комбинации фильтров,
пагинацию, историю, задержку поиска, отмену устаревшего запроса и адаптивное расположение панели.

## Регистрация и авторизация

Страницы `/signup` и `/signin` открывают формы, `/account` — защищённый личный кабинет.
Регистрация сразу выполняет вход. Email регистронезависимый и уникальный; пароль —
от 8 до 128 символов. Формат запроса проверяется схемами, сгенерированными из `main.tsp`.

API: `POST /api/auth/signup`, `POST /api/auth/signin` принимают JSON `{ email, password }`
и возвращают `{ id, email }`; `GET /api/auth/me` возвращает того же пользователя либо 401.
`POST /api/auth/signout` удаляет текущую сессию в PostgreSQL и очищает cookie.
Занятый email возвращает 409, неверные credentials — 401; ошибки имеют формат `ApiError`.

Миграция `003_create_users` добавляет пользователей и серверные сессии. Пароли сохраняются
как scrypt-хеши с независимой случайной солью (N=65536, r=8, p=2), токены сессий —
только как SHA-256-хеши. Cookie `psparts_session` имеет HttpOnly, SameSite=Lax и срок 7 дней.
Сессия переживает перезапуск сервера; истёкшие сессии не авторизуют и очищаются при создании новых.
В production cookie по умолчанию Secure; локальный Compose явно отключает Secure для HTTP.
При прямом запуске `COOKIE_SECURE` позволяет переопределить это поведение. Для HTTPS оставьте
Secure включённым. Если прокси изменяет Host, задайте `APP_ORIGIN` точным публичным origin
(без завершающего `/`). Cross-site POST-запросы отклоняются. Пароли и cookie не отправляются в Sentry.

Проверки после запуска Docker Desktop:

```bash
npm run test:contract
docker compose up --build -d --wait
npm run test:e2e -- --workers=2
```

Playwright проверяет регистрацию, вход, выход с повторным использованием старой cookie,
дублирующий email, неверный пароль, перезагрузку и прямой переход гостя в кабинет.
Адрес берётся из `BASE_URL` (по умолчанию `http://127.0.0.1:3000`). Тесты создают уникальных
пользователей: запускайте их только против тестовой базы. Существующий CI запускает их вместе
с остальными E2E после сборки и ожидания готовности контейнеров.

## Окружение и мониторинг

Скопируйте `.env.example` в `.env` и заполните значения для своего окружения.
Секреты не коммитятся. В Compose URL локальной БД задан отдельно; для прямого запуска API
передайте `DATABASE_URL` и обязательный `PORT` через окружение. `.env` автоматически не загружается
при прямом запуске Node: экспортируйте значения или используйте `node --env-file`. `PORT` проверяется
как целое число от 1 до 65535; запасного порта в коде нет. В Compose порт задаётся конфигурацией.
На хостинге используйте URL managed PostgreSQL.

| Переменная                 | Назначение                                                      |
| -------------------------- | --------------------------------------------------------------- |
| `DATABASE_URL`             | Соединение API с PostgreSQL, только runtime                     |
| `PORT`                     | Порт Fastify; хостинг задаёт сам, локально 3000                 |
| `SENTRY_DSN`               | DSN бэкенда, runtime                                            |
| `SENTRY_ENVIRONMENT`       | Метка окружения Sentry                                          |
| `VITE_SENTRY_DSN`          | Публичный DSN фронтенда, передаётся при сборке                  |
| `SENTRY_TEST_ENABLED`      | Временно включает `/api/debug-sentry`                           |
| `VITE_SENTRY_TEST_ENABLED` | Временно включает страницу `/monitoring-test`, нужна пересборка |

Без DSN мониторинг отключён. Инициализация Node SDK выполняется до загрузки Fastify.
React использует SDK и ErrorBoundary. Для проверки доставки событий заполните DSN,
временно включите оба тестовых флага и пересоберите приложение. Нажмите кнопку на
`/monitoring-test` и запросите `/api/debug-sentry` (ожидается 500).
Проверьте обе ошибки в проектах Sentry, затем отключите флаги и пересоберите образ.
Тесты только в локальном окружении не подтверждают доставку событий с продакшена.

Для полностью локальной проверки SDK без настоящих DSN используйте тестовый приёмник:

```bash
POSTGRES_PORT=55432 docker compose -f compose.yaml -f compose.monitoring.yaml up --build -d --wait
```

Откройте `http://localhost:3000/monitoring-test`, нажмите кнопку и запросите
`http://localhost:3000/api/debug-sentry`. На `http://localhost:4318/events` должны
появиться `Frontend monitoring smoke test` и `Backend monitoring smoke test`.
Этот приёмник хранит только тестовые сообщения в памяти; не публикуйте его в интернете.
После проверки верните обычную сборку и остановите приёмник:

```bash
POSTGRES_PORT=55432 docker compose -f compose.yaml -f compose.monitoring.yaml stop sentry-local
POSTGRES_PORT=55432 SENTRY_DSN= VITE_SENTRY_DSN= SENTRY_TEST_ENABLED=false VITE_SENTRY_TEST_ENABLED=false docker compose up --build -d --wait
```

DSN фронтенда доступен в JS-бандле. `SENTRY_AUTH_TOKEN` для базового сбора ошибок не нужен;
если настраиваете загрузку source maps, передавайте токен как build secret, не как `VITE_*` или Docker ARG.

## Проверка и форматирование кода

### TypeSpec → OpenAPI

Из корня репозитория:

```bash
npm ci
npm run contract:generate
```

Источник контракта — `main.tsp`, настройки генератора — `tspconfig.yaml`.
Результат — `openapi/openapi.yaml` (OpenAPI 3.1.0). Файл генерируется автоматически:
изменяйте TypeSpec и повторяйте команду, не редактируйте YAML вручную.
Для форматирования TypeSpec: `npm run typespec:format`.
Обязательные точки с запятой в TypeSpec сохраняются: правило JS/TS `semi: never` на него не распространяется.

Описаны `/health-check`, `/api/categories`, `/api/products`, `/api/products/{id}`,
операции авторизации и общие модели `Money` и `ApiError`.
`Money` — `{ amount: 1999000, currency: "RUB" }`: неотрицательное целое количество копеек
в пределах безопасного целого JavaScript. В API товар содержит `price: Money` вместо `price_kopecks`;
в БД по-прежнему хранится `price_kopecks`, сервер преобразует его на границе API.
`ApiError` — `{ statusCode, error, message }`, для некорректного запроса возвращается 400,
неизвестной категории — 404, внутреннего сбоя — 500 без технических подробностей в ответе.

Цепочка единого источника правды:

```text
main.tsp → openapi/openapi.yaml
         → apps/api/src/generated/schemas.ts
         → apps/api/src/generated/api.d.ts
         → apps/front/src/generated/api.d.ts
```

`openapi-typescript` генерирует типы, `scripts/generate-contract.mjs` проверяет OpenAPI через
Swagger Parser, разрешает ссылки и извлекает JSON Schema из операций. OpenAPI 3.1 позволяет
использовать JSON Schema 2020-12 напрямую. Ajv в Fastify проверяет параметры запросов
и ответы; ручные интерфейсы Category/Product на фронтенде заменены сгенерированными типами.
Генератор поддерживает JSON body/response и query/path/header параметры; другие форматы
нужно явно добавить в генератор, а не описывать второй контракт вручную.

```bash
npm run openapi:generate # только OpenAPI
npm run contract:generate # OpenAPI + backend schemas + types
npm run contract:check # регенерация и сравнение с закоммиченными артефактами
npm run test:contract # негативные тесты Money, ошибок и Fastify-валидации
```

Все файлы `generated` и OpenAPI коммитятся вместе с TypeSpec. Их не правят руками и не
форматируют отдельно: генератор сам применяет стиль проекта. CI проверяет актуальность
артефактов до сборки. Изменение API начинайте с `main.tsp`, затем генерируйте, адаптируйте
обработчики и интерфейс, запускайте проверки и коммитьте весь результат.

Фильтр товаров: `GET /api/products?category=processors`. Slug проверяется по схеме;
допустимы строчные латинские буквы, цифры и дефисы между группами, длина 1–100.
Статические страницы и условный тестовый маршрут Sentry не входят в публичный API-контракт.
Генерация не требует запущенного сервера, PostgreSQL или `DATABASE_URL` и выполняется отдельно от сборки приложения.

### Браузерные тесты

Playwright запускает Chromium против уже работающего приложения; перед тестами
ожидает до 60 секунд успешный JSON-ответ `/health-check`.

```bash
npm ci
npx playwright install chromium
POSTGRES_PORT=55432 docker compose up --build -d --wait --wait-timeout 180
BASE_URL=http://127.0.0.1:3000 npm run test:e2e
```

`BASE_URL` задаёт адрес тестируемого приложения и имеет приоритет над альтернативной
переменной `PLAYWRIGHT_BASE_URL`. По умолчанию используется `http://127.0.0.1:3000`.
Для проверки через dev-сервер Vite: запустите его и укажите `BASE_URL=http://127.0.0.1:5173`.
API и PostgreSQL должны быть запущены; Vite проксирует API и health-check.
При проверке Хекслетом передайте предоставленный проверкой адрес через `BASE_URL`.
Тестовые файлы используют только относительные пути; локальный сервер принудительно не поднимается.

```bash
npm test
npm run test:e2e:ui
npm run test:e2e:report
```

Проверяются каталог и авторизация, фильтры, пагинация, история и JSON 404 неизвестного API.
UI-селекторы используют `data-testid` из чеклистов: `nav-catalog`, `catalog-list`, `catalog-item`,
`catalog-item-name`, `catalog-item-price`, `catalog-item-availability`, `catalog-empty`,
`catalog-filters`, `filter-category`, `filter-price-min`, `filter-price-max`, `filter-available`,
`filter-search`, `filter-reset`, `catalog-pagination`, `catalog-page-prev`, `catalog-page-next`.

Workflow `Quality` запускается на каждый push и pull request. Он устанавливает зависимости
и Chromium, проверяет линтер и сборку, собирает Docker-образ, запускает PostgreSQL и приложение,
ждёт healthy-статуса, проверяет API и повторный сид, затем выполняет браузерные тесты.
Ошибки тестов не игнорируются, автоматических повторов нет. HTML-отчёт, скриншоты,
видео и traces упавших тестов сохраняются в GitHub Actions artifacts на 7 дней.

### Только зелёный main в продакшене

Эти настройки задаются в GitHub/Render отдельно и не включаются изменением локальных файлов:

1. В GitHub Settings → Rules → Rulesets создайте правило для `main`: изменения только
   через pull request, обязательный успешный check `Build and browser tests`, ветка должна
   быть актуальна относительно `main`. Не разрешайте обход правила и прямые push.
2. В Render привяжите сервис к `main` и выберите Auto-Deploy → After CI Checks Pass
   вместо On Commit. Репозиторий должен быть подключён через GitHub-интеграцию.
3. После push проверьте успешный `Quality` в Actions. Локальный зелёный прогон
   не означает, что облачный CI уже выполнился.

Общая конфигурация ESLint проверяет JavaScript и TypeScript в обоих приложениях.
Правила похожи на Airbnb: строгие сравнения, `const`, стрелочные колбэки,
порядок импортов, запрет изменения параметров и неиспользуемых переменных.
Неиспользуемые параметры TypeScript можно обозначать префиксом `_`.
Это адаптированный набор правил, а не полный `eslint-config-airbnb`.
Для React включены правила hooks и проверка зависимостей эффектов.

Prettier отвечает за оформление: два пробела, одинарные кавычки,
отсутствие необязательных точек с запятой и завершающие запятые. `eslint-config-prettier` отключает
конфликтующие правила ESLint, а правило `semi: ['error', 'never']` после него закрепляет
стиль без точек с запятой. Сборки, зависимости и покрытие исключены из проверок.
